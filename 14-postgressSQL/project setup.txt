PART 3 — Create Prisma schema
Step 8 — Create User model

Open:

prisma/schema.prisma

Use:

generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
  runtime  = "nodejs"
}

datasource db {
  provider = "postgresql"
}

model User {
  id        Int      @id @default(autoincrement())
  name      String   @db.VarChar(100)
  email     String   @unique @db.VarChar(255)
  createdAt DateTime @default(now()) @map("created_at")

  tasks Task[]

  @@map("users")
}

Notice the mapping:

Prisma              PostgreSQL

User          →     users
createdAt     →     created_at

This allows us to keep JavaScript-friendly camelCase while preserving the existing SQL naming style.

Step 9 — Create Task model

Add:

model Task {
  id          Int      @id @default(autoincrement())
  userId      Int      @map("user_id")
  title       String   @db.VarChar(255)
  description String?
  status      String   @default("pending") @db.VarChar(20)
  priority    String   @default("medium") @db.VarChar(20)
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @default(now()) @map("updated_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("tasks")
}

Step 10 — Understand the relationship

This:

userId Int

is the actual foreign-key column.

This:

user User

is the Prisma relation.

And:

tasks Task[]

means one User can have many Tasks.

Conceptually:

User
 │
 │ 1
 │
 ├───────────<
             many
             │
             ▼
           Tasks

Equivalent SQL:

FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE

Step 20 — Create user
export const createUser = async (req, res) => {
  try {
    const { name, email } = req.body;

    if (!name || !email) {
      return res.status(400).json({
        message: "Name and email are required",
      });
    }

    const user = await prisma.user.create({
      data: {
        name,
        email,
      },
    });

    res.status(201).json(user);
  } catch (error) {
    console.error(error);

    if (error.code === "P2002") {
      return res.status(409).json({
        message: "Email already exists",
      });
    }

    res.status(500).json({
      message: "Failed to create user",
    });
  }
};

Equivalent SQL:

INSERT INTO users (name, email)
VALUES ($1, $2);

export const updateUser = async (req, res) => {
  try {
    const id = Number(req.params.id);
    const { name, email } = req.body;

    if (Number.isNaN(id)) {
      return res.status(400).json({
        message: "Invalid user ID",
      });
    }

    if (!name || !email) {
      return res.status(400).json({
        message: "Name and email are required",
      });
    }

    const user = await prisma.user.update({
      where: {
        id,
      },
      data: {
        name,
        email,
      },
    });

    res.status(200).json(user);
  } catch (error) {
    console.error(error);

    if (error.code === "P2002") {
      return res.status(409).json({
        message: "Email already exists",
      });
    }

    if (error.code === "P2025") {
      return res.status(404).json({
        message: "User not found",
      });
    }

    res.status(500).json({
      message: "Failed to update user",
    });
  }
};

    });
  }
};

Step 27 — Get tasks
export const getTasks = async (req, res) => {
  try {
    const {
      status,
      priority,
      search,
      sortBy = "createdAt",
      order = "desc",
      page = 1,
      limit = 10,
    } = req.query;

    const pageNumber = Number(page);
    const limitNumber = Number(limit);

    const skip = (pageNumber - 1) * limitNumber;

    const tasks = await prisma.task.findMany({
      where: {
        ...(status && { status }),
        ...(priority && { priority }),

        ...(search && {
          OR: [
            {
              title: {
                contains: search,
                mode: "insensitive",
              },
            },
            {
              description: {
                contains: search,
                mode: "insensitive",
              },
            },
          ],
        }),
      },

      orderBy: {
        [sortBy]: order,
      },

      skip,
      take: limitNumber,

      include: {
        user: true,
      },
    });

    res.status(200).json(tasks);
  } catch (error) {
    console.error(error);

    res.status(500).json({
      message: "Failed to fetch tasks",
    });
  }
};

This single Prisma query demonstrates several important concepts:

where
OR
contains
mode
orderBy
skip
take
include

PART 15 — migrate dev vs migrate deploy

Remember this:

During development

When you change:

schema.prisma

use:

npx prisma migrate dev --name add_something

Example:

schema.prisma
      ↓
migrate dev
      ↓
new migration
      ↓
local database
Deploying an existing migration

Use:

npx prisma migrate deploy

Example:

existing migrations
       ↓
migrate deploy
       ↓
Neon / production database
PART 16 — db push vs migrations

You should also remember:

npx prisma db push

means:

Synchronize the database schema with the Prisma schema without creating migration history.

Whereas:

npx prisma migrate dev

means:

Create a migration, record the schema change, and apply it.

For a proper project with migration history, prefer migrations.

Final end-to-end flow

If you're explaining this project in an interview, you can describe it like this:

“I built a Node.js and Express Task Manager API using Prisma ORM with PostgreSQL. I first defined the database models and relationships in Prisma schema, then used Prisma migrations to create and track the database schema. Prisma Client handles CRUD operations from the Express controllers. I implemented filtering, searching, sorting, pagination and relational queries using Prisma's query API. I initially used local PostgreSQL for development and then migrated the database schema to Neon PostgreSQL using Prisma's migration system. The application uses the pooled Neon connection at runtime, while the direct connection is used for Prisma CLI migrations.”

That's a very solid MERN developer interview explanation because it demonstrates that you understand both the ORM and the underlying SQL database rather than simply knowing Prisma syntax.
